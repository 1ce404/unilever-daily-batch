# 写底稿：先讲通一件事，再按意思分段

2026-11-05 用户反馈：每组同结构、文案串联弱、没有活人感。新稿使用 `copy_logic_version: 2`。这次改的是本地创作要求、参考稿选择、整篇审读和本条脚本的改写上下文，不自动改产品共享提示词，不自动重写旧稿或开始生产。

## 1. 每条先定说服思路，再比较整组

排期拆 brief 后，由 Agent 阅读当天任务、产品配置和可用画面，逐条填写 `creative_plan`。这一部分需要创作判断，不能由脚本随机选一个模板代替。

```json
{
  "creative_plan": {
    "speaker": "替油头男生解释选购思路的朋友，不假装亲测",
    "audience_question": "选控油洗发水时，怎么把清爽和蓬松两个需求一起考虑？",
    "angle": "从选购标准聊起，避免先抱怨头发油再报产品名",
    "throughline": "先说清自己想要的发根状态，再用产品已核实的卖点解释推荐理由",
    "route": ["把清爽和蓬松作为两个选购需求提出", "用本条测试卖点解释这款为何值得考虑", "把需求明确的人引到直播间核对活动"],
    "ending_bridge": "推荐给确实有这两个需求的人，活动信息帮助其继续做选择"
  }
}
```

- `speaker` 是表达视角和立场，要与产品受众相容；不编使用经历、朋友评价、专业身份或数据背书。
- `audience_question` 是观众的一个具体疑问，`throughline` 是整篇准备怎么回答它。若无法一句话说明，先缩小论点。
- `route` 写至少两个有先后关系的具体思路，说明为什么接着讲下一件事。不要只填「钩子→痛点→产品→卖点→效果→CTA」或镜头标签。节点不等于最终分段，段数不固定。
- 同组每条要在观察、疑问或推理路径上有实质差别。同一卖点可以从选择标准、回应犹豫、解释画面细节、比较不同需求等角度展开，但这些只是启发，不是轮流套用的新模板库。
- 用户指定结构写进 brief 的 `template`，尊重该结构；仍需要思路与句间承接，不为了差异强行重排。
- 先读已存在的计划，避免重复。`draft.py` 在请求平台前检查所有待生成 brief：缺计划、同产品路径逐字相同会拦下。语义近似却换了标签仍需 Agent 比较，不能依赖机器。

## 2. 只使用明确给出的方向

默认不搜索当天热榜，不创建 `hotspots.json`，也不为脚本补热梗。用户或当天排期明确给出热点、口头禅或表达方向时，写进对应 brief 的 `direction_hint` 或 `creative_plan`，并核对产品事实、画面和合规边界。旧运行目录里的 `hotspots.json` 仍可供原任务重写时复现，不作为新一天的输入要求。

## 3. 平台先写全文，再按意思回填分段

```bash
python3 -I scripts/draft.py --config $C --run $R --dry-run
python3 -I scripts/draft.py --config $C --run $R
python3 -I scripts/draft.py --config $C --run $R --brief <id> --redo
```

`--redo` 会删除这条原来的平台脚本并重写，原审读和人审结论失效。不要因为更新 skill 就重写既有任务。

创作要求最多 2000 字，优先完整保留：本条说话立场、核心疑问、主张和推进；排期的方向/卖点/受众；产品事实、机制、CTA、规则、素材边界和禁用词。必要要求超限会报错，请精简表达后重试，不能截掉尾部事实。

剩余空间再放参考稿、同组切入、近期重复开头和审核人的改法。参考稿先按卖点/方向筛选，在同等相关稿中按 brief 轮换，不再每次塞相同的头几篇。带上 `speaker` 和 `why`；空间允许才带参考全文。没有确认稿时可用标明「未确认参考」的稿，不能把它说成用户认可。

文案要求：

- 围绕一个问题讲完一件事，先写能连贯朗读的全文，再按完整意思分段；输出仍是平台脚本，不额外塞进要念出来的分析。
- 每句接住上句，并推进一个判断。卖点解释本条的推荐理由，不把成分、效果、品牌背景都独立凑一段。
- 产品出现位置服从思路；首次引入说完整产品名，后续指代明确即可。第一次讲卖点时要清楚它属于哪个产品，不每段重复全名。
- 具体观察与判断构成说话口吻。避免每段重新招呼观众，避免靠「兄弟/姐妹/真的/直接冲」或感叹号制造活人感。
- CTA 接住本条的购买理由。促销机制按 config，不突然插入与全文无关的囤货口号。
- 素材标签描述画面库存，不是写稿顺序。口播里的观察和动作要有现有画面支撑，不编需要专门镜头的情节，不要求画面展示抽象成分的功效因果。
- 平台默认「4~6 段」是编排参考，不能据此复制段落功能。若共享提示词与本条要求冲突，检查实际输出并说明冲突；不把不合格输出当作完成，也不擅自改共享提示词。

平台写完会按排期命名、查硬性问题，自动要求修改一轮。还存在问题由 Agent 定位后修改；不要为了满足词数或关键词，把单句补丁塞进不连贯的全文。

## 4. 整篇审读：必须读实际成稿

每条读一遍完整口播，整组再比较一遍。不能从计划或 lint 通过推断稿子合格：

1. 开头抛出的疑问后文是否真的回答？能否用一句话说清整篇主张？
2. 相邻两段为什么这样接？是观察到解释、疑问到回答、标准到产品依据，还是单纯并列凑信息？有指代悬空或重复开场就改。
3. 是否同一说话人、同一立场一路讲完？有没有假装亲测、空泛夸赞、术语堆砌和突然喊口号？
4. CTA 为什么在此出现？推荐对象、购买理由和活动信息是否顺接？
5. 和同组其它稿的疑问/推进有何实际区别？去掉产品名再读，仍是同一个故事换词就重写，不以相似度低为通过依据。

修改后按当前实际文本记录 JSON。以下仅为字段示意，判断与承接必须根据实际稿逐条写，不能复制这份示意或让脚本自动填「通过」：

```json
{
  "verdict": "pass",
  "throughline": "说明实际成稿如何回答它开头的问题，必要时引用短句",
  "voice": "说明说话立场与具体措辞，指出是否存在虚构经历或播报腔",
  "distinctness": "写出比较的 brief ID，以及核心疑问或推理过程的实际区别；只有一条时说明这一范围",
  "transitions": [
    {"from": "1", "to": "2", "link": "具体说明第二段怎样接住第一段的观察或疑问"},
    {"from": "2", "to": "3", "link": "具体说明为何接到第三段；每个相邻边界都要解释，包含 CTA"}
  ]
}
```

```bash
python3 -I scripts/review_doc.py editorial --config $C --run $R --brief <id> --assessment <JSON路径>
python3 -I scripts/lint_copy.py --config $C --run $R
python3 -I scripts/review_doc.py render --config $C --run $R
```

审读记录绑定文案和创作计划的 hash。改过任何一个就要重读。这个命令只记录 Agent 的编辑判断，不改变 `status`、不创建用户批准；字段齐全不等于审美通过。Markdown 待审稿先展示思路、完整口播，再展示可编辑分段；飞书表展示思路与分段全文。用户审核仍是必需步骤。

## 5. 机器能检查什么

- 产品全名完整出现；不能被标点拆开。首次卖点有明确产品归属；不强制第三段才出现，也不强迫已引入的产品反复报全名。
- 指定测试卖点、结尾 CTA 词；已有价格/机制不得超出 config；节点词缺失和过期机制会提醒。
- 禁用词、极限词/时间承诺、串系列词、emoji 和会被念出来的语音指令。
- 字幕短句按显示宽度算，>20 报错、>12 提醒；整条建议75~150字，超出为提醒，不是时长保证。
- 去掉产品名、卖点术语、机制后的非 CTA 文字，与范本、近7天同产品底稿、当天其它底稿比较，相似度>35%报错。相同段序且同位置至少两个句头相同也报错（用户指定结构时不查后者）。
- 同产品完全相同的声明路径报错；新稿未整篇审读或审读后改过会报错。

机器不证明因果成立、文风自然、语义结构不同或画面一定匹配。人审看实际稿；批量改写按原段对应，不能期待它自动创造新的整篇结构。

## 6. 审过的稿怎样批量改写

`submit` 同步审过的文案，仍然每段开启改写，包含 CTA。新稿把本条 speaker、question、throughline、route 和 ending_bridge 作为**这条脚本**的 `vo_rewrite_prompt` 补充：先读全文，保持同一立场、指代和承接，再按原 id 回填，不逐段重新开场。保留脚本已有其它改写要求，回读核对成功后才生成；不修改产品共享提示词。

同一底稿的版本仍共享说服路径，结构差异要在底稿层建立。`poll` 查改写后的硬性问题；该步骤仍不能证明每条衔接自然。若反复破坏同类承接，要说明平台改写约束问题，不能把技术生成成功当成文案验收。

## 产品事实的来源

清扬在 `config/qingyang/<产品>.json`，力士在 `config/lux/<产品>.json`，品牌共用规则在 `config/<品牌>.json`。价格机制需要用当天资料核对。把新事实或卡审词改到相应 config；用户确认稿入 gold，编辑修改入 learned。不要在本说明复制一份会过期的价格、卖点或禁用词清单。
